# بنية الواجهة الجديدة — Technical Architecture

**النمط:** تطبيق واجهة أحادي الصفحة باستخدام HTML/CSS وES Modules أصلية (بدون إطار خارجي).

**الهدف:** فصل التقديم التسويقي عن إدارة حساب العميل، مع توحيد الهوية والاحتفاظ الكامل بالعقد السابق. لم يُنسخ أي ملف CSS/مكوّن واجهة من مشروع المصدر.

## الأجزاء

1. `main.js`: Router مبني على History API مع مسارات المشاركة والتوافق.
2. `marketing.js`: مشاهد مستقلة للمنتجين، وتحميل الصور الأصلية دون ادعاءات حالة الاتصال.
3. `knowledge.js`: يقرأ بيانات JSON الأصلية ويقدّم مكتبة بحث وتصنيفات وصفحات قابلة للمشاركة.
4. `auth.js`: إجراءات التسجيل والدخول وتأكيد البريد وإعادة التعيين.
5. `account.js`: لوحة العميل بمساحة عمل وتبويبات منظمة مرتبطة بالأذونات وحالة الحساب القادمة من API.
6. `api.js`: طبقة وحيدة للطلبات، ترسل Cookies تلقائيًا، مع JSON وFormData ومعالجة أخطاء HTTP وواجهات Proxy الفاشلة.
7. `style.css`: Tokens للألوان والمسافات، وCSS للمنتجات والدليل واللوحة والهواتف، دون الاعتماد على CSS المصدر.

## سياسات الأمان

- لا يُخزن أي Token في LocalStorage أو SessionStorage.
- الاستجابات النصية التي تظهر ضمن HTML تُمرر بدالة escaping، وروابط الفتح الخارجية تُقيّد إلى HTTP/HTTPS.
- المعلومات المالية وحالات الخدمة والاشتراك تقتصر على ما يعيده السيرفر.
- لا يوجد استدعاء مباشر إلى عنوان السيرفر من متصفح العميل؛ يُستخدم `/api/customer/*` عبر Netlify.
- لم تُخزن أرقام حسابات بنكية ثابتة ضمن واجهة الحساب؛ تعتمد دائمًا على `/config`.
- لا يوجد تحكم مالي/ VPN مستقل من الواجهة.

## المقايضات

- مجلد `dist` هو توزيع ملفات ثابتة وليس bundle JavaScript مضغوطًا أو مترجمًا؛ هذا يقلل الاعتماديات لكنه لا يحقق تحزيم Vite أو Code Splitting الآلي.
- مركز المعرفة الكامل يُحمّل بيانات محتواه عند بدء التطبيق؛ للأحمال الكبيرة مستقبلًا يمكن تحويله إلى تحميل انتقائي أو Static Pre-rendering.
- كل مسارات الواجهة الصريحة لا تتطلب اتصالًا بالخادم إلا صفحة الحساب والإجراءات الحساسة. فشل فحص الجلسة لا يؤخر تحميل واجهات التسويق.
- إعادة إنتاج متطلبات React/TypeScript تحتاج مشروع نقل هندسي منفصل، ولا يجوز وصف هذه النسخة بأنها تستخدمهما.
